# franciscoribeiro2003.github.io — v3

Personal site: a terminal-flavoured home, a file-system view of projects, a
photography room, and a globe of every route I have ridden.

**Static HTML on GitHub Pages. PocketBase on Cloud Run is the source of truth,
read at runtime.** This repo ships no content — no JSON, no geometry, nothing
about the rides. Edit a stage description in the admin UI and it is live on the
next page load, with no deploy.

---

## How it is put together

```
index.html            home — profile card + Windows-8-style tile mosaic
projects/             file-system explorer listing the project entries
projects/<slug>/      one project — GENERATED at deploy time, gitignored
photography/          geolocated gallery: places / albums / timeline
map/                  MapLibre globe + travel journal
blog/                 typographic post index
blog/<slug>/          one post — GENERATED at deploy time, gitignored
404.html
sitemap.xml robots.txt   generated by tools/prerender.mjs

css/
  tokens.css          design tokens (light + dark), mirrors the Figma variables
  base.css            reset, type ramp, page shell
  components.css      nav, footer, tiles, tree, tags, timeline
  pages.css           per-page layouts
  markdown.css        rendered post bodies (post pages only)
  guestbook.css       the notebook overlay

js/
  core/site.js        theme, language, terminal prompt, nav + footer
  core/i18n.js        EN/PT strings
  core/data.js        PocketBase REST client + stale-while-revalidate cache
  core/normalize.js   record → view-model shaping (shared with the prerenderer)
  core/markdown.js    markdown → DOM: parse, harden, enhance
  core/sketch.js      guestbook page model: strokes, text boxes, PNG export
  guestbook.js        the notebook
  pages/*.js          one entry point per page
  pages/post.js       one post, either type

tools/
  post-shell.html     template for a generated per-post page
  prerender.mjs       PocketBase → the <head> SEO block, sitemap, and one
                      shell per post
                      (the only build step; CI runs it on every deploy)
```

Only the `<head>` is generated at build time. Everything in the body is
fetched from PocketBase in the browser.

### The repo holds no content — not even the generated head

`tools/prerender.mjs` writes the `<head>` in place, which is right at deploy
time and wrong in git. Committing its output had left ~30 KB of names, job
titles, project abstracts and trip statistics in the page files.

So the committed HTML carries the markers and nothing between them, and CI
runs the prerenderer on a fresh checkout before deploying. Locally:

```bash
npm run prerender    # fill the heads to inspect them
npm run seo:reset    # empty them again — run before committing
npm run seo:check    # non-zero if anything generated is still in the tree
```

Because there is no committed `<head>` to fall back on, a failed prerender now
**fails the deploy** instead of exiting 0. It retries three times first, for
the backend's cold start. Continuing would publish pages with no title.

Facts about the site's owner are records too: `webpage.name`,
`job_title_pt/en`, `locality`, `country`, the CV as `webpage.cv`, the footer's
source link as `webpage.repo_url`, and the email and profile URLs derived from
`webpage.contacts`. The site chrome fills them in once the profile loads —
`applyIdentity()` in `js/core/site.js` — and the CV link stays hidden until it
has somewhere to point.

### The guestbook

A visitor gets one page, not a form. A pen draws anywhere on it; handwritten
text boxes can be added, moved, re-edited and deleted. The page is flattened to
a **transparent PNG** in the browser and posted to PocketBase, and the book
renders those PNGs over its own paper — which is why they carry no background.
The editing tools only appear once you turn to the blank page at the end, and
that page lands on the left or the right depending on how many are already
signed.

The model is vector and normalised 0..1 (`js/core/sketch.js`), so it re-renders
at any page size, exports crisply at any resolution, and undo is a pop. Strokes
are traced as quadratic curves through the midpoints of pointer samples rather
than straight segments, and `getCoalescedEvents()` recovers the samples the
browser collected between frames — a fast gesture otherwise gets one point per
frame, which is exactly the faceted line that reads as "not smooth".

Export cost, measured at 840 × 1120: a signature and a line of text is ~29 KB,
twenty strokes ~130 KB, a densely scribbled page ~330 KB. A thousand pages at
300 KB is under a cent a month in Cloud Storage, so the size cap is a guard
against a pathological upload rather than a budget to optimise against.

Nothing appears in the book until it is approved in the admin UI.

### Posts: the blog and the projects are one collection

A project and a blog entry differ only in what kind of thing they are, so
`posts.type` is a field (`blog` · `project`, extensible) and the two endpoints
are filtered views of one collection. Each entry carries a bilingual title,
description and **markdown** body, a date, a cover, an optional outbound link
(GitHub, YouTube, Medium, LinkedIn), tags, and its own SEO fields.

Those SEO fields are why each entry gets a page of its own. A crawler is handed
one file per URL, so an entry can only carry its own title and description if
it has its own address. `tools/prerender.mjs` writes one shell per published
post from `tools/post-shell.html`, filling in the `<head>` and leaving the body
as the same runtime-fetched shell as every other page. The generated files are
never committed.

The cost of that is one deploy: **a new post needs a build to get its URL.**
Editing an existing post is still live on the next page load.

Markdown is rendered by `js/core/markdown.js`, which parses with `marked`
(pinned, with an SRI hash), then walks the parsed tree deleting everything off
an allowlist, then enhances what is left — headings demoted so the page keeps
one `h1`, tables and code in their own scroll containers, external links given
`rel="noopener noreferrer"`, and images lazily loaded with no referrer.

The hardening walks a `DOMParser` tree rather than sanitising an HTML string,
because a detached document is inert — no script runs and no `onerror` fires
until a node is adopted — and because regexes over HTML have already broken
this project once.

Images referenced from a body must be **external URLs**; nothing is uploaded
alongside a post, and an `<img>` whose src is not http(s) is dropped.

## The GPX problem, and where it is solved

57 Strava exports, **263 MB**, ~988 000 track points at 1 Hz. Raw GPX must
never reach SQLite: there is no spatial index, and streaming megabytes of
geometry through a scale-to-zero container is the worst possible path.

So the geometry is simplified **once, locally**, and uploaded. That pipeline
lives with the backend, not here — see `../fribeiro/README.md`:

```bash
cd ../fribeiro
npm run tracks     # GPX → .build/   988,512 → 15,605 points (−98.4%)
npm run upload     # .build/ → PocketBase
```

```
263 MB of GPX  →  0.33 MB of per-stage tracks + 0.51 MB overview
```

Two shapes, because the map asks two different questions:

| Where | What | Fetched |
|---|---|---|
| `map_assets.routes` | all 57 routes at overview fidelity | once, when the map opens |
| `stages[].track_file` | one stage at full detail (≤ 13 KB) | when a visitor opens that stage |
| `map_assets.clouds` | fog-of-war mask, three bands | once, when the map opens |

**One request per view, not per item.** The globe's landing state is a single
file rather than 57 fetches through a backend that has to cold-start.

### Adding a trip

Done in `../fribeiro`. Nothing about the rides touches this repo.

The upload matches on natural keys — trips by slug, stages by track id — so it
adds only what is new, never duplicates, and **never overwrites the
descriptions, regions or stories written in the admin UI**. Verified: after
editing a stage description and a trip region, a full re-run reported
`0 created, 63 updated` and left both edits intact.

Stage names, numbers and dates come from Strava's own track names
("Étape 5: Loupian->Aubais" → stage 5, "Loupian → Aubais"). Order is
chronological from the GPX timestamps, because the filename numbering in this
archive has gaps, a "4.5", and a rest day.

### Elevation

Climb is computed from the **full** track, resampled every 20 m and smoothed
over ~100 m — never from the simplified geometry, and never from raw 1 Hz
deltas. At 1 Hz a rider climbing 600 m/h gains ~0.17 m per sample, so a naive
"ignore deltas under 1 m" noise filter throws away nearly all the real gain.
Getting this wrong reported 704 m across 4 800 km; the correct figure is
**42 136 m**.

### The clouds

Real 3D geometry in a MapLibre custom layer (`js/core/clouds3d.js`). Placement
rules live in `js/core/clouds.js`.

**Four attempts came before this.** Each is the obvious thing to reach for and
each fails, so they are worth recording:

1. **fBm noise pattern** in a polygon — self-similar fog, no distinct masses.
2. **Billowed, domain-warped fBm** — depth, but `1 - |n|` creases into veins,
   so it read as marbled paper.
3. **Clustered puffs as a `fill-pattern`** — looked like cloud in isolation and
   was still completely wrong on a globe: patterns tile, MapLibre subdivides
   them further on zoom so the seams multiply, and the polygon boundary puts a
   hard straight edge at the radius.
4. **Shaded sprites as `symbol` icons** — discrete objects at last, and the
   radius finally behaved as a spawn rule. But `icon-pitch-alignment: map`
   lays a billboard flat on the surface like a decal, so tilting showed a
   sticker, and a fixed silhouette reads as a peanut from every angle.

A texture cannot be a cloud, and neither can a billboard. So each cloud is now
a cluster of five to nine ellipsoid puffs positioned in 3D above the sphere.
Rotating the globe slides the near puffs across the far ones, the shading
changes with the viewing angle, and clouds occlude each other.

**Projection.** The vertex shader uses MapLibre's own prelude —
`projectToSphere` for the position on the unit sphere,
`globeGetRotationMatrix` for the local surface frame, `globeComputeClippingZ`
and `u_projection_matrix` — so the geometry lands exactly where the map's own
layers do. Offsets are in metres, divided by `GLOBE_RADIUS`. Opacity is
multiplied by `projectionTransition`, so the clouds are gone by the time the
globe has flattened into mercator, which is also where cloud cover stops
meaning anything.

**Shape.** A cloud picks one of four archetypes — fair-weather cumulus,
congestus, a wide flat stratus sheet, a wind-drawn streak — which differ in
proportion, not just in size, and each is given a random heading. Within a
cloud the puffs are hierarchical: three to five large core lobes carry the
mass, then fourteen to twenty-six smaller detail lobes hang off them, giving
about 23 puffs per cloud across a 20:1 size range.

That hierarchy is the point. With five to nine equal spheres per cloud you
could count them, and the first version looked like clusters of polystyrene
balls: one recipe stamped across the planet with a hard, countable silhouette.

**Coverage, not just size.** Size alone did not sell the undiscovered world:
with 900 clouds the masses were large but sparse, and the whole of North
Africa stayed legible at 2 000 km from any route. Three things now scale with
distance — how many clouds exist, how large they are, and how thick they are.
Measured sky coverage:

```
    0–200 km      0% cover, 0.0 layers   clear over what I have ridden
  200–450         1%        0.0
  450–700        23%        0.2          scattered puffs appear
  700–1100       71%        1.2
 1100–1800       98%        4.5
 1800–2600      100%        8.6          solid
 2600+           98%        4.1
```

Named checks: Porto, on a route, has nothing overhead. North Africa at 2 000 km
has seven clouds over it. Australia, 14 000 km away, has four.

Remote clouds carry far fewer detail lobes, since detail is invisible at that
distance — that is what pays for tripling the count. The collar tier is
sampled out to `REMOTE_KM` rather than `farKm`, because the global tier alone
is too sparse to make the middle of the ramp opaque.

The exponents were tuned against these measurements rather than guessed:
`spawnProbability` is `t^1.6` (squared left 200–700 km almost empty, which
read as a wall), size is `remoteness^1.4`, and `REMOTE_KM` came down from
4 500 to 2 600 because the ramp was reaching full strength too far out.

**No depth writes.** This is what made the spheres countable. Writing depth
etched each puff's silhouette into the buffer, so overlapping puffs showed
their intersection curves as hard creases — the faceted look. With
`depthMask(false)` the puffs accumulate and merge into one soft mass. The far
side of the globe is still handled, by the clipping plane in the vertex shader
rather than by depth.

**Translucent, and thickening with distance.** Material opacity is 0.6, and
per-instance thickness runs from 0.34 near the boundary to 1.0 deep in the
unknown. The point is a map that is
hidden but still there, so the land reads faintly underneath and density comes
from puffs overlapping rather than from any one being solid. This is not the
transition fading out — the transition is still purely where instances stop
existing.

**Shading.** The light wrap was reduced from 0.65 to 0.28. The wide wrap meant
nothing was ever in shadow, which is what made the puffs look like wax. The
silhouette alpha now falls off as `pow(facing, 1.9)` with a per-fragment hash
breaking up the rim, so the outline dissolves instead of ending in a clean arc.

**Honest ceiling.** This is stylised, not photoreal. A union of lit ellipsoids
can read convincingly as a cloud field at globe distance, but it will never
have the wispy fractal fringes or the internal light scattering of the real
thing. That needs raymarching a 3D density field, which is a different and far
more expensive piece of work.

**Cost.** One instanced draw call: a once-subdivided octahedron (32 triangles)
× ~40 600 puffs ≈ **1.3 million triangles a frame**, 1.3 MB of static buffers,
nothing uploaded per frame. The budget went into puff count rather than
tessellation, since the detail lobes are small on screen.

**The radius is still a spawn rule.** Nothing is generated within 200 km of a
trip's bounding box; between 200 and 1100 km the probability of a cloud
existing ramps up; beyond that it is 1. The boundary is where instances stop,
so it is ragged. Measured:

```
0–200 km        0 clouds     clear sky over what I have ridden
200–350         1
350–500        10
500–650        22
650–800        35
800–950        95
950–1100      155
beyond 1100  2130           the world I have not seen
```

Sampling is two-tier. One uniform pass does not work: the transition band is a
thin collar around six boxes in Europe, a rounding error next to the area of
the planet, so uniform candidates almost never land in it. The first attempt
put 2 578 clouds beyond the far radius and 22 inside the band — a wall, not a
thinning.

**Verified before shipping**, since a globe frame cannot be rendered in the
development harness: MapLibre 5.6.0's shader source was read rather than
recalled, and the cloud shader was compiled and linked against the real globe
prelude in a bare WebGL context. All four instance attributes resolve. That
check caught four bugs: backticks inside a GLSL comment silently terminating
the template literal, unclamped latitudes producing tile coordinates from -151
to 9940 against a valid range of 0–8192, puffs placed at ground level and at
170 km because the vertical jitter was scaled by radius instead of altitude,
and 246 km puffs against an intended 130 km cap.

It did **not** catch the one that mattered most. `defaultProjectionData`
returns `tileMercatorCoords` of `[0, 0, 1, 1]`, so a custom layer must pass
positions in mercator [0, 1] — not the [0, 8192] tile units a tiled layer
uses. Passing tile units collapsed every cloud to the south pole. The check
that missed it asserted the coordinates were inside [0, 8192]: a passing test
against the wrong invariant, which is worse than no test, because it was
reported as verified. The placement is now checked by reimplementing
`projectToSphere` and `globeGetRotationMatrix` in JavaScript and confirming six
locations round-trip to their exact longitude and latitude.

**Sizes on zoom.** The sprite version used `interpolate exponential 2` with
stops at z0/z6/z10, which is wrong: MapLibre applies the base to the fraction
*between stops*, not to the zoom value, so clouds were up to 4.4× too large
around z1–z2 and only correct at the three stop points. Geometry in metres
sidesteps the problem entirely — a cloud is a fixed size on the ground because
it is a fixed size in the world.

### Route colours

Routes are bright red with a glow, because red is the complement of the teal
ocean and green land the satellite imagery is made of, and nothing else on the
map competes with it.

Three stacked lines from the same geometry make the glow: a wide, heavily
blurred halo, a tighter brighter one, and a crisp core. `line-blur` does the
work — no shader needed. The dark casing that used to sit under the route is
gone: a dark outline around a glowing line cancels the glow it exists to
support.

Glow strength is a compromise, and the reason is worth writing down. How well
a glow reads depends on what is under it: over dark ocean a red halo adds
light and looks like glow, but over pale desert or snow it darkens the ground
and looks like a smear. Tested against ocean, desert, forest and snow, a halo
strong enough to be striking on water turned the Sahara into a pink wash. The
values in the code are the strongest that stay clean on light terrain.

- more glow → raise `line-opacity` on `routes-halo` (0.36) and `routes-glow`
  (0.72), or widen them
- less glow → lower the halo opacity first; it is the layer that muddies pale
  ground

A white-hot core was tried and rejected: striking on the ocean, but over
desert it read as a white line and lost the red identity entirely.

A selected route runs white-hot (`#fff0ec`) rather than switching hue, so it
reads as the same route turned up rather than a different kind of thing. The
pointer handlers are bound to the glow layer, not the core — the core is under
two pixels wide at globe zoom, and the glow gives a 6–14 px hit target for the
same geometry.

Each transport mode still has its own colour, and the mode chips carry a
matching swatch so the filter doubles as the legend. Cycling is `#ff3b2a`;
hiking, boat and train are defined and appear the day a trip uses one.

### Why not vector tiles or DuckDB

- **PMTiles.** The right answer for large archives. At 0.51 MB of overview
  geometry it would add a pmtiles client, a tiling step and per-tile round
  trips to solve a problem that does not exist yet. Revisit when the overview
  passes a few megabytes.
- **DuckDB-WASM.** ~35 MB of WebAssembly, and it does not render anything —
  MapLibre still needs the geometry handed to it. Where it *would* earn its
  place is a stats page (km per year, climbing histograms) over Parquet with
  range requests.

## Cold starts, and what is done about them

Cloud Run scales to zero, so the first request after an idle period takes a
second or two. That is the real cost of reading the backend at runtime — not
money: the Cloud Run free tier is 2 million requests a month, which a personal
site will not approach.

Two mitigations in `js/core/data.js`:

1. **Stale-while-revalidate.** A cached copy paints immediately and the network
   response replaces it when it lands, so a returning visitor never waits.
   Fresh for 5 minutes, usable for 7 days.
2. **One request per view.** Content is one round of parallel collection reads;
   the map's landing state is one file.

A warm second visit does **2** requests instead of 12.

## SEO

The body is JS-rendered, which is fine for Google and useless for everything
else — Bing, DuckDuckBot and the link-preview bots behind LinkedIn, WhatsApp,
Slack and Mastodon read the raw HTML only. So `npm run prerender` bakes the
`<head>`:

- `<title>`, description, keywords, canonical, Open Graph, Twitter cards
- JSON-LD: a `Person` graph on every page, plus `WebSite`, `ItemList`
  (projects), `ItemList`/`TouristTrip` (trips and stages), `Blog`, and
  `BlogPosting`/`CreativeWork` on a post's own page
- one generated shell per published post, so each has an indexable URL
- `sitemap.xml`, listing every page and every post that is not `noindex`, and
  `robots.txt`

It reads `page_seo` straight from PocketBase and exits without touching the
HTML if the backend is unreachable, so a cold instance can never publish empty
meta tags.

> An earlier version also injected rendered content into the body. It was
> removed: it matched closing tags with a regex, which silently corrupts the
> document as soon as the injected markup nests the same tag, and re-running
> duplicated the blocks. Rewriting HTML needs a real parser; the head does not.

> JSON going into a `<script>` element has its `</` escaped to `<\/`. An HTML
> parser ends a script at the first `</script>` in the raw text no matter what
> the JSON quoting says, so a post that merely *mentions* a closing script tag
> — normal enough in a technical blog — would otherwise cut the JSON-LD in half
> and spill the rest into the document as live markup. That was a real bug here,
> caught by a test post containing `<script>` and `<img onerror>`.

### Editing the SEO copy

`page_seo` in PocketBase, one record per page: `title_pt/en`,
`description_pt/en`, `keywords`, `og_image`, `noindex`.

Each post carries its own set — `seo_title_pt/en`, `seo_description_pt/en`,
`seo_keywords`, `og_image`, `noindex` — used on that post's generated page.
Anything left empty falls back: the description to the post's own
`description_*` and then to the opening of the markdown body; the social image
to the cover. So a post is never published with an empty card, and a post you
have written SEO for uses exactly what you wrote.

The prerender step warns when a title passes 60 characters or a description
passes 160 — where Google starts truncating.

## Running it locally

Two processes: PocketBase (the backend) and the site.

```bash
cd ../fribeiro && npm run pb   # PocketBase (first-time setup in its README)
cd -            && npm run dev # the site
```

- site → http://localhost:4321
- PocketBase admin → http://localhost:8090/_/

`js/config.js` (gitignored) points the site at the backend. Copy
`js/config.sample.js` and set `pocketbaseUrl`.

`npm run dev` prerenders before serving. That is not optional polish: the
per-post pages at `/projects/<slug>/` and `/blog/<slug>/` are *generated*, so
without that step those URLs 404 locally while working fine in production. If
the backend is down it prints why and serves anyway, so you can still work on
CSS.

`npm run prerender` finds the backend from `js/config.js` when
`POCKETBASE_URL` is not set, so a local run needs no environment variable.

### The dev server

`tools/dev-server.mjs`, not `python3 -m http.server`, for two reasons that
each cost real debugging time:

- **No caching.** Python sends no cache headers, so browsers apply their own
  heuristic and hold on to ES modules. You edit `js/core/site.js`, reload, and
  the old module is still running — the change looks broken when it is only
  invisible. Every response here is `no-store`. (If a browser already cached
  the old files from the python server, one hard reload clears it.)
- **404 like production.** GitHub Pages serves `404.html` for unknown paths.
  Python serves its own plain-text page, so local and production disagreed
  exactly where you would want them to agree.

### Ports

`4321`, because the obvious ones are taken on macOS: `5000` and `7000` by
ControlCenter (AirPlay Receiver), `8000` and `8080` by Docker Desktop.

### Keep pb_data off the bind mount

Run the local container with `pb_data` on a **Docker volume**, not a macOS bind
mount. SQLite over Docker Desktop's file sharing does not get reliable POSIX
locking, and concurrent reads produce intermittent
`disk I/O error (522)` and `database disk image is malformed (11)`.

That is not theoretical — it happened during development: a page issuing 11
parallel collection reads returned HTTP 400 for most of them while
`PRAGMA integrity_check` still reported `ok`. Moving `pb_data` to a volume
fixed it completely. It is the same class of hazard as the GCS FUSE mount in
production.

## Things worth knowing before extending this

**PocketBase has no geospatial support.** No PostGIS, no SpatiaLite. Anything
spatial — simplification, buffering, distance, bbox — happens offline in
`tools/`.

**SQLite on Cloud Storage is not safe for concurrent writes.** GCS FUSE does
not provide the POSIX file locking SQLite needs, and Cloud Run's filesystem is
per-instance and ephemeral. Your service already caps **max instances at 1**,
which is the thing that makes this survivable — keep it that way, and add a
scheduled backup. The guestbook is the only write path from the site.

**Satellite tiles are not free forever.** The default is Esri World Imagery,
which needs no key and is fine for a personal site with attribution. Set
`satelliteTiles` in the config to move to MapTiler or Mapbox.

**Content lives in PocketBase, not in a file.** The SEO copy, the CV facts and
the stage descriptions are all edited in the admin UI. The schema generator in
`../fribeiro/tools/` emits structure only.

## Deploying

Push to `main`. The workflow writes `js/config.js` from repository secrets,
prerenders the SEO head from PocketBase, stamps the build date into the footer,
and publishes to `gh-pages`.

| Secret | Purpose |
|---|---|
| `POCKETBASE_URL` | runtime content + the build-time SEO prerender |
